# 远程桌面插件：设计与实现

> 状态：已完成并通过本机冒烟测试；**尚未在浏览器里实际操作验证**（见第 7 节）
> 更新：2026-09-02
> 关联：`agent/desktop_agent.py`（用户态采集与注入）、`backend/server.py`（鉴权与转发）、
> `ui/panel.html`（画面与交互）、`backend/autostart.py`（开机自启）

## 1. 决定性约束：服务看不到桌面

这是整个设计的起因，先说清楚，否则后面的双进程结构看起来像过度设计。

Dbox 的插件跑在 `extensions_host` 里，而它是一个 **NSSM Windows 服务**。Windows 自 Vista
起把服务隔离到 **Session 0**——那里没有用户的桌面。所以：

- 在插件后端里截图，拿到的是 Session 0 的空桌面，不是用户看到的画面；
- 在插件后端里注入键鼠，也到不了用户正在用的会话。

这不是代码技巧能绕过的，是系统级隔离。TeamViewer / RustDesk / AnyDesk 受同样的约束，
解法也一致：**在用户会话里跑一个代理进程**。

于是架构是双进程：

```
浏览器面板 ──HTTP──> 插件后端（服务内，Session 0）
                         │ 127.0.0.1:18921
                         ▼
                    桌面代理 agent（用户会话，Session 1）
                    ├ 屏幕捕获（GDI BitBlt）
                    ├ 光标补画
                    ├ 输入注入（SendInput）
                    └ JPEG 编码
```

后端只做三件事：鉴权、转发、把单帧拼成 MJPEG 流。真正的脏活都在 agent。

## 2. agent 的启动：会话守护（开机即就绪，含登录界面）

> 更新：2026-09-06。原「计划任务 ONLOGON」方案已由 `backend/sessiond.py` 的会话守护取代。

agent 要出画面、要能注入键鼠，就必须跑在**当前正在显示的那个桌面**上。而哪个桌面在显示
是会变的：登录后是 `WinSta0\Default`，登录界面 / 锁屏 / UAC 是 `WinSta0\Winlogon`。
所以「怎么启动」的本质是：**谁**在**什么时候**把它放到**哪个桌面**。

答案：插件后端本身就是 AUTO_START 的 LocalSystem 服务（开机即运行，早于任何登录），
守护线程常驻其中，持续把 agent 投递到当前显示桌面：

| 当前状态 | 投递目标 | 判定依据 |
| --- | --- | --- |
| 已登录 | `WinSta0\Default` | 会话内无 LogonUI 且能取到用户令牌 |
| 登录界面 / 锁屏 | `WinSta0\Winlogon` | LogonUI.exe 在跑，或该会话取不到用户令牌 |

令牌取自服务自身的 SYSTEM 令牌（复制成主令牌后把 `TokenSessionId` 改到目标会话，需
SeTcbPrivilege），**不是** `WTSQueryUserToken`——后者在没人登录时直接失败，那正是
「重启后停在登录界面就连不上、人被锁在外面」的根因。SYSTEM 身份还顺带解决了 UIPI：
代理以 `S-1-16-16384`（System 完整性）运行，发出的输入不会被任何窗口丢弃。

于是：**开机即用，无需任何手动初始化**；面板不再要求用户点「安装自启 / 启动代理」。
旧的 `ONLOGON` 计划任务作为兜底保留（代理单实例，端口被占会自动退出，不会冲突）。

实现要点（都是实测踩出来的）：

- **必须先复制令牌**再改 `TokenSessionId`：直接改本进程令牌会把整个服务进程挪到别的会话。
- 令牌与进程创建走 **ctypes 直调 Win32**，不用 pywin32 的 `DuplicateTokenEx` 包装——
  实测该包装在 4 参 / 5 参两种写法下一律返回 1346（ERROR_BAD_IMPERSONATION_LEVEL）。
- ctypes 必须**显式声明 argtypes/restype**：否则 64 位 HANDLE 会被截成 32 位，
  `GetCurrentProcess()` 伪句柄失效，后续调用一律报「句柄无效」(WinError 6)。
- 位置判定失败时**绝不能杀**现有 agent：判断不了位置就按「位置正确」处理，
  否则新版上线会误杀正在出画面的旧版，新的又没起来，直接失联。

## 3. 三个需求的实现

### 3.1 断网重连

分两种断，处理方式不同：

| 断的是什么 | 表现 | 处理 |
| --- | --- | --- |
| 浏览器 ↔ Dbox | `<img>` 触发 error | 指数退避自动重连（1→2→4→8→15s 封顶）+ 「⟳ 重连」按钮手动立即重连 |
| Dbox ↔ agent | 抓帧失败 | **流不中断**，改喂一张占位帧（降到 1fps），等 agent 回来自然恢复 |

第二点是有意的：如果 agent 一掉线就把流断掉，前端 `<img>` 立刻 error 并触发重连风暴，
而重连也解决不了 agent 没起来的问题——只会让服务端和浏览器都白忙。持续喂占位帧能保持
连接，画面上也明确写着「桌面代理未连接」。

另外：连续 3 次抓帧失败才降级为占位帧。偶发单帧失败（比如正好赶上分辨率切换）不该让
用户看到画面闪一下。

浏览器侧的 `online` 事件也会触发重连（网络恢复时不必等退避计时）。

### 3.2 省流量模式

三档预设，展开「⚙」后可逐项微调：

| 档位 | 帧率 | JPEG 质量 | 分辨率 | 静止不推帧 |
| --- | --- | --- | --- | --- |
| 流畅 | 15 | 72 | 100% | 关 |
| 均衡 | 8 | 60 | 100% | 开 |
| 省流量 | 3 | 42 | 70% | 开 |

微调项：帧率 1–30、质量 20–95、分辨率 30–100%、灰度、静止不推帧。

**实测**（1536×864 桌面）：

```
全画质                116 KB/帧   244 ms
省流量（含灰度）       48 KB/帧    70 ms   省 58%
省流量（彩色）         53 KB/帧    82 ms   省 54%
```

灰度用单通道 JPEG（`Image.convert('L')` 后直接存），比转成 RGB 再存省约三成，画面偏色
但文字完全可读，是流量紧张时性价比最高的一档。

**静止检测踩过一次坑**：最初用整帧 md5 精确比对，实测连续两帧 hash 永远不同——桌面上
几乎总有秒级变化（任务栏时钟、加载动画、光标闪烁），于是「静止不推帧」形同虚设。
改成把画面降采样成 64×36 的灰度指纹、比较平均像素差（阈值 2.5/255）后，静止时连续四帧
hash 完全一致。静止期间 agent 连 JPEG 编码都跳过，直接复用上一帧数据。

### 3.3 放大缩小

- 适应窗口 / 100% / ±（25%–400%），底部实时显示当前比例。
- 坐标映射不需要为缩放额外换算：`<img>` 的 CSS 尺寸就是「屏幕尺寸 × 缩放比」，所以
  `屏幕坐标 = (点击位置 - 图片左上角) / 图片显示宽度 × 屏幕宽度` 对任何缩放比都成立。
- 放大后画面超出视口时：中键拖拽平移，或用滚动条。
- **Ctrl + 滚轮 = 本地缩放**，不发给远程；普通滚轮发给远程滚动。二者必须区分，否则
  想缩放的时候会不停滚动对方的页面。

## 4. 输入

- 鼠标移动按 30ms 节流（再密也只是白烧流量），停手后补发最后一个位置，避免差半格。
- 键盘走 `SendInput` 的 `KEYEVENTF_UNICODE`：直接发字符而不是虚拟键码，**中文等输入法
  内容能正确上屏**，不必维护整套键盘布局映射表。
- 面板里有一个隐藏 `textarea` 接管输入：输入法组合期间交给 `compositionend`，避免把
  拼音中间态当字符发出去。
- 触摸端：单指拖动＝移动、轻点＝左键、双指＝右键。

## 5. 安全边界

- 所有端点要求登录；`/stream` 因为 `<img>` 带不了请求头，用 `?token=`（沿用 codebuddy
  的 SSE 鉴权先例）。
- agent 只监听 `127.0.0.1`，不对外暴露；单实例（端口被占说明已有实例在跑，直接退出）。
- 输入注入是全权操作（等同于把鼠标键盘交给对方），日志会记录自启安装行为。

## 6. 依赖

**没有新增任何 pip 包**。屏幕捕获用 `pywin32` 的 GDI，编码用 `Pillow`，输入注入用
`ctypes` 调 `SendInput`，这三个都已在 `requirements.txt` 里。

## 8. 遗留可选项

- **分块差异传输**：**已实现**（见第 9 节）。原估计「要引入前端 canvas 合成，复杂度上升明显」——
  但前端自第一版起就是 `fetch + ReadableStream` 读 multipart 并画进 canvas，且已支持
  `X-Frame-Rect` 把子区域贴到画布指定绝对坐标，这套「补丁合成」基础设施本来就建好了，
  所以实际工作量只在 agent/后端，复杂度远低于原估计。
- **剪贴板同步**、**文件拖放**：标准远程桌面的高频需求，目前没有。
- **多显示器单独选择**：现在始终抓整块虚拟屏，可以加个「只抓主屏 / 指定某块屏」。
- **空闲自动降帧**：检测到无人操作超过 N 分钟自动切到最低档。

## 9. 差分传输（I/P 帧式脏矩形）

> 状态：已实现（agent + 后端 + 前端开关）。更新：2026-09-03

### 9.1 动机

原省流量只靠「降帧率 / 降质 / 降分辨率 + 整帧静止跳过」。静止跳过是**整帧二元**的：
要么整屏没变（整帧不推），要么整屏"有变"（整帧重发）——而桌面上永远有秒级微变
（任务栏时钟、光标闪烁、加载动画），于是只要有一像素变，整张图（或整个 ROI）都得重传，
哪怕 99% 的像素和上一帧一模一样。这正是视频编码里"只有 I 帧、没有 P 帧"的状态。

### 9.2 方案（类 VNC/RFB 的 dirty-rectangle）

- agent 常驻**上一帧捕获图**（捕获分辨率 RGB）。每拍把当前帧切成 32×32 tile，逐 tile
  与上一帧比对（PIL `ImageChops.difference` 取灰度最大差，超过阈值 `DIFF_THRESHOLD=12`
  即认为该块变），合并成最少矩形。
- 变了的矩形各自编码成小 JPEG，带 `X-Frame-Rect`（虚拟屏绝对坐标）作为一帧发出
  （**P 帧补丁**）；前端已有逻辑把它贴到画布对应位置，只更新变化区域。
- 每 `KF_INTERVAL=45` 拍（≈8fps 下约 5.6s）或 ROI 移动 / 首帧，强制发一次**整帧关键帧**
  （**I 帧**）以校正前端画布累积漂移。关键帧强制原生分辨率，保证前端画布锁定为整屏虚拟
  分辨率、补丁坐标对齐；补丁可按 `scale` 降采样以省带宽。
- 完全没变（无脏矩形）→ agent 返回 `X-Frame-Empty:1`，后端整拍跳过，**零流量**。
- **光标天然免费**：agent 每帧重绘光标，移动时旧位置与新位置各产生一个脏矩形，等价于
  VNC 的光标独立编码，无需额外机制；静止时光标区也只在它真动时才传。

### 9.3 传输与前端

- 复用既有 multipart + `boundary=frame` + `X-Frame-Rect` 机制：agent 把一拍内的多个补丁
  （及关键帧）拼成带各自 `X-Frame-Rect` 的 multipart 体（不带结束边界），后端原样转发。
- 前端 `fetch + ReadableStream` 逐帧解析、按 `rect` 贴到持久化整屏画布；空拍自然跳过（缓冲
  积累、下一拍再补），无需改动。新增「差分传输(P帧)」开关（默认开），关闭则退回整帧模式。

### 9.4 ROI 协调

ROI 模式下 agent 只抓该区域、与上一拍同区域比对；补丁坐标加 ROI 偏移还原成虚拟屏绝对
坐标，前端在其整屏画布上对位合成。ROI 移动 → 区域变更 → 强制关键帧，避免错位。

### 9.5 价值与边界

- **收益最大场景**＝用户开省流量时的静态内容（看文档 / 写代码 / 浏览）：稳态只传光标、
  插入符等几百字节小补丁，相对原整帧方案可降 1~2 个数量级。
- **不占优场景**＝看视频 / 连续滚动：每帧大半屏变化，差分≈整帧，应继续用降帧/降质/降分辨率。
- **防漂移**：关键帧周期发送 + ROI 变更重建，漂移被限制在 `KF_INTERVAL` 拍内。
- 小补丁用 JPEG 仍有文件头开销，但相对整帧仍可忽略；如需极致可改 PNG/原始 RLE（前端硬编码
  jpeg 解码，故当前统一 JPEG，未引入 Content-Type 分支）。
